# Glossary

## A

**API surface** – The total set of HTTP endpoints (method + path combinations) exposed by an API, as defined in an OpenAPI specification.

**Annotation** – A keyword embedded in a test description (e.g. `@businessRule`, `@flow`, `@security`) that allows the analyzer to associate the test with a specific coverage category.

## B

**Boundary value** – A test that exercises the extreme edges of a valid input range (e.g. the minimum and maximum allowed values for a numeric parameter).

**Business rule** – A named, documented constraint or behaviour that the API must enforce (e.g. "users with more than 5 orders receive a 10% discount"). Defined in `business-rules.yaml`.

## C

**Circuit breaker** – A resilience pattern that stops calling a failing downstream service after a configurable number of consecutive failures, returning an error immediately until the service recovers.

**CLI** – Command-Line Interface. The primary interaction model for the analyzer: `node dist/index.js <command> [options]`.

**Contract testing** – Verifying that an API provider (server) satisfies the expectations of its consumers, typically using Pact or similar consumer-driven contract testing frameworks.

**Coverage gap** – An item (endpoint, parameter, business rule, flow step, etc.) that is present in the spec or rules but not exercised by any test.

**Coverage percent** – `coveredItems / totalItems × 100`. The headline metric for each coverage type.

## D

**Dashboard** – The built-in UI (Vite + React) that visualises all coverage reports in a single interactive web app.

## E

**Endpoint** – A unique combination of HTTP method and URL path (e.g. `GET /users/{id}`).

**Endpoint coverage** – The percentage of API endpoints defined in the OpenAPI spec that are exercised by at least one test.

**Exclusion** – A path glob or HTTP method configured in `config.yaml` to be ignored during analysis (e.g. `/internal/*`, `OPTIONS`).

## F

**Flow** – See *integration flow*.

**Format** – The output format of a report: `json`, `html`, `csv`, or `junit`.

## I

**Integration flow** – A multi-step sequence of API calls that together represent a complete user journey (e.g. search → add to cart → checkout → payment).

**Integration flow coverage** – The percentage of defined integration flows that are fully exercised by tests.

## J

**JMeter** – [Apache JMeter](https://jmeter.apache.org/), a load-testing tool. Its `.jtl`/`.csv` output files can be passed to the `perf-resilience-coverage` command via `--load-results`.

**JUnit XML** – A standardised XML format for test results. Generated by the `junit` report format and parsed by most CI systems (Jenkins, GitHub Actions, etc.) to surface pass/fail status.

## K

**k6** – An open-source load-testing tool from Grafana Labs. Its JSON summary export (from `k6 run --summary-export`) can be passed to `--load-results`.

## O

**OpenAPI** – A language-agnostic HTTP API description format (formerly Swagger). The analyzer supports OpenAPI 3.x and Swagger 2.x.

**OWASP API Security Top 10** – A list of the most critical security risks for APIs published by the [Open Web Application Security Project](https://owasp.org/www-project-api-security/).

## P

**Pact** – A consumer-driven contract testing framework. Pact JSON files describe the expected request/response interactions between a consumer and a provider.

**Parameter** – An input to an API endpoint, which may appear in the path, query string, request header, or request body.

**Parameter coverage** – The percentage of parameters tested across four categories: valid, boundary, missing, and invalid.

**Plugin** – A JavaScript file that exports an `analyze` function, implementing a custom coverage dimension beyond the built-in commands.

**Performance coverage** – The percentage of API endpoints for which load-test data (JMeter/k6) exists and meets the configured response-time and error-rate thresholds.

## R

**Report** – The output of a coverage analysis. Available in JSON, HTML, CSV, and JUnit formats.

**Resilience** – The ability of a system to recover gracefully from failures. Resilience coverage tracks whether tests exercise patterns such as retry, circuit breaker, timeout, bulkhead, and fallback.

**Resilience coverage** – The percentage of API endpoints or services for which resilience test scenarios are present.

## S

**Scenario** – A sub-item within a business rule or integration flow that represents a specific test case (e.g. `first-time-buyer` within the `discount-eligibility` rule).

**Security coverage** – The percentage of defined security scenarios (authentication, authorisation, injection, rate limiting, data exposure) that are covered by tests.

**Spec** – An OpenAPI specification file (YAML or JSON) that describes the API surface.

## T

**Threshold** – A minimum coverage percentage below which the analyzer exits with a non-zero code, causing CI to fail. Configurable per coverage type in `config.yaml` or via `--threshold-*` CLI flags.

**ts-node** – A TypeScript execution engine for Node.js that allows running `.ts` files directly without a separate build step.

## V

**Valid value** – A test that sends a well-formed, in-range value for a parameter, verifying the happy-path behaviour.

**VitePress** – The static site generator used to build this documentation site.
